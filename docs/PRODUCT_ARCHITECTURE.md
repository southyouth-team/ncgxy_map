# 南昌工学院数字校园产品架构（V1）

状态：产品基线。产品形态为二维地图 + 三维数字空间 + 空间社交；位置默认隐藏，主动授权后按精度展示。首个落地校园为南昌工学院主校区。

## 1. 产品定位
以真实校园空间为基础，提供地图导航、建筑与室内空间、三维沉浸体验及实时互动。产品不是“地图附加聊天室”，而是以统一空间实体为核心的数字校园平台。

## 2. 产品分层
### 二维地图
校园总览、地点搜索、POI、建筑详情、室外导航；显示符合隐私规则的聚合在线人数。建筑/房间 Feature 必须绑定现实空间实体。

### 建筑与室内空间
统一管理建筑、楼层、房间、走廊、楼梯、电梯、大厅。室内导航依赖几何和可通行连接；未核验数据不得作为正式导航依据。

### 三维数字空间
Three.js 场景绑定现实建筑、楼层和空间。Avatar 只代表虚拟位置；用户未开启现实位置共享也可移动 Avatar。首期仅做场景加载、空间进入、基础移动和切换。

### 空间社交
聊天室、成员列表、活动和后续语音房间挂载到空间或活动会话。会话与建筑/房间实体解耦，支持建筑公共会话、房间会话、活动会话。

## 3. 核心用户流程
搜索建筑 → 查看详情 → 选择楼层/房间 → 进入三维场景 → 加入空间会话 → 与成员交流。位置共享必须独立操作，不能因进入虚拟空间自动开启。

## 4. 统一空间实体原则
- campus_feature：地图绘制要素。
- campus_building：现实建筑。
- campus_floor：现实楼层。
- campus_space：房间、走廊、楼梯等。
- campus_scene_binding：现实实体与三维模型映射。
一个建筑可对应多个地图版本、多个楼层和多个模型；不得把 Polygon、GLB 或 Avatar 坐标当作建筑主记录。

## 5. 隐私规则
- location_visibility 默认 hidden；可选 building、space。
- space 只展示楼层/房间业务身份，不展示精确室内坐标。
- 服务端校验共享授权、校园成员关系、空间权限和屏蔽关系。
- Redis 保存短期 presence，使用 TTL/心跳；退出、关闭共享或超时后清理。
- 不建立默认的个人精确位置历史轨迹。
- 虚拟 Avatar 状态与现实位置共享使用不同字段、事件和权限。

## 6. 治理能力
社交开放前必须有用户屏蔽、举报、消息审核/删除、空间访问策略、限流和管理操作审计。访客、校园成员和管理员权限分离。

## 7. 多校园扩展
学校数据以 campus 隔离；地图、空间、场景、用户和实时模块共享。每个查询和写操作都校验 campus_id。

## 8. V1 不做
不宣传演示场景为测绘成果；不默认采集/公开现实位置；不首期做语音视频、复杂 Avatar 动画和虚拟经济；不提前拆微服务。
