## 1. 产品定位

建设一个 AI 原生、可运行、可交互、可持续修改和保存的 Three.js 3D 世界沙盒（AI Native 3D World Engine），而不只是 AI 3D 模型展示器。

用户能够通过自然语言创建和修改模型/场景；模型作为世界对象进入沙盒；玩家角色能够在世界中移动并与对象交互；环境变化和玩家行为能够驱动世界状态；世界可保存并恢复。

## 2. 当前 MVP 目标与范围

### 2.1 必须打通的核心闭环

1. 创建独立 Three.js 沙盒场景，具有明确世界尺寸、坐标系和地面。
2. 通过 AI 文本（可选参考图）生成独立 Three.js 模型；模型是沙盒子对象/资产实例，不替换原校园建筑或底图。
3. 模型进入沙盒后可选择、移动、旋转、缩放、复制、删除；同一模板/模型定义可有多个独立实例。
4. 玩家角色能够在沙盒中移动，识别附近可交互对象并执行交互。
5. 环境支持时间、天气、风等状态，并由统一运行时驱动可见效果。
6. 沙盒保存与刷新恢复模型、变换、环境和必要的对象状态。
7. AI 能通过对话修改模型整体或部件，并可动态增加模型参数；参数定义与参数值分离，界面按元数据动态呈现。
8. 环境、交互、状态和运行时有清晰边界，允许后续扩展全局/局部环境、太阳光照、设备和房间交互。

### 2.2 MVP 非目标

- 不重建完整校园 GIS 编辑器，不替换校园现有地图/建筑数据。
- 不要求一次实现完整室内装修系统、NPC 自主智能、多玩家在线、语音、复杂经济系统。
- 不要求一次实现真实天文级太阳计算；先打通可验证的虚拟日周期，再扩展真实日期/地理位置。
- 不为每种模型类别硬编码一套专属交互 UI 或参数白名单。
- 不执行 AI 任意生成的 JavaScript/TypeScript 于主线程；代码执行必须隔离，世界配置与行为由受控运行时消费。
- 不为架构完整性一次性建设所有大型引擎子系统；先实现核心闭环。

## 3. 已确认的架构原则（决策基线）

### 3.1 世界对象不是单纯 Mesh

逻辑对象应逐步具备以下能力，具体能力按对象需要选择，不要求每个对象都实现全部字段：

- 几何/视觉表示（一个或多个 Three.js Object3D/Mesh）。
- 稳定唯一 ID、对象类型、版本与元数据。
- Transform（位置、旋转、缩放）。
- 自身状态（如门的 open、灯具的 enabled、设备的 running）。
- 可选交互入口（Interactable）。
- 可选环境响应/绑定（Environment Bindings）。
- 可选物理表示（碰撞体、质量、运动属性）。
- 可选空间归属和关系（World/Zone/Building/Floor/Room）。
- 生命周期与持久化数据。

Mesh 名称不得作为稳定身份；对象 ID、部件 ID、组件 ID 和关系 ID 应独立维护。模型定义与沙盒实例 Transform 分离；同一模型定义可以实例化多次。

### 3.2 四个核心系统

1. **Environment System**：管理环境定义、环境值、全局环境、局部环境区域及环境实体（太阳等）。
2. **Interaction System**：管理玩家/对象交互检测、交互入口、条件和动作请求。
3. **State System**：统一管理世界、区域、模型、部件和设备的状态及状态变更。
4. **Runtime System**：把状态和事件转换成 Three.js 光照、阴影、材质、动画、物理、音频等运行效果。

系统通过明确 API、状态更新和事件协作；避免交互系统直接修改任意 Mesh 材质，或环境系统直接耦合某个模型的内部实现。

### 3.3 全局环境与局部环境

环境变量不是固定的 `time/weather/wind` 三字段集合。变量定义与当前值分离，并由元数据驱动控制界面。

- **Global Environment**：默认作用于整个世界，例如时间、天气、全局风场、重力、基础温度。
- **Local Environment**：作用于区域、建筑、楼层、房间或指定对象，例如局部风、局部降雨、室内温度、局部湿度。
- **继承与覆盖**：局部环境默认继承全局值；只有显式覆盖的变量才采用局部值。应定义覆盖优先级与恢复继承行为。
- **动态注册**：AI/用户可创建、修改、删除环境变量定义；变量类型和 UI 控件由元数据决定。至少考虑 number、boolean、enum、color、vector 等类型。
- **模型响应规则**：模型/部件可订阅环境变量并声明效果，例如树冠随风摆动、表面受雨湿润。规则不是环境变量本身。

### 3.3.1 环境变量开关、参数与作用范围

每个环境变量至少区分三个维度，不能用数值为 0 代替禁用状态：

- **Enabled**：该变量/效果是否参与运行；关闭不应清空用户设置的参数值。
- **Parameters**：该变量的业务参数，例如小时、天气类型、风速、风向、降雨强度。
- **Scope / Override**：变量作用于全局还是局部区域/对象；局部未声明时继承全局，显式 enabled=false 必须覆盖全局，不能被继承逻辑重新打开。

组合开关需要有明确的父子语义：天气总开关关闭时，所有天气子效果均不生效；天气总开关开启时，降雨等子效果可独立启停；风力开关关闭时不施加风场，但保留用户配置的风速/风向值。

当前 M0 只实现已有 Runtime 能力对应的开关：时间光照联动、天气总开关、降雨子开关、风力开关。温度、湿度、重力等在尚无对应模拟 Runtime 前不伪装成可用功能；后续注册变量时再提供相应开关和参数元数据。

持久化必须保存开关本身和参数值。旧版 v1 存档迁移时，缺少的 enabled 字段按 true 处理，以保持旧存档原有环境表现。

### 3.4 太阳与全局光照

太阳是世界级环境实体/天体系统，不是普通模型绑定，也不是一个孤立的 AI 模型。

- 时间系统提供时间输入；后续可加入日期、时区、纬度、经度。
- Solar System 计算太阳方向/高度角。
- Lighting Runtime 管理 DirectionalLight、天空/环境光、阴影和昼夜色彩。
- 全局太阳光照统一影响所有符合投影/接收规则的对象；对象通过 castShadow/receiveShadow 等能力参与阴影。
- 第一阶段先做可调时间驱动的虚拟日周期；真实太阳轨迹作为后续增强。
- 需要考虑阴影相机范围、bias、阴影分辨率、更新频率和性能分级。

### 3.5 人物交互与对象状态

“开灯”这类人为行为由 Interaction System 发起，而不是把“开灯”硬编码为环境变量。

标准链路：

玩家输入 → 交互检测 → 交互动作请求 → 条件/权限判断 → State System 更新对象状态 → 事件通知 → Runtime 更新光照/动画/音频/UI。

示例：墙壁开关是 Interactable；灯具维护 enabled 状态；开关动作切换灯具状态；Lighting Runtime 根据灯具状态更新实际光源。开关与灯具通过稳定对象 ID/关系配置关联。

交互动作应是可扩展的受控能力（如 toggle、set、open、close、use、pickup、drop、enter、activate），由对象配置声明，不为每个模型写专用业务分支。AI 可以生成对象交互配置，但不能提供任意可执行代码。

### 3.6 事件系统

State System 的状态变更应能够发出事件，让 Lighting、Animation、Audio、UI、AI 等订阅者解耦响应。事件至少覆盖玩家交互、对象状态变化、环境变化、物理碰撞、对象生命周期。高频帧数据不得逐帧持久化。

### 3.7 世界数据与渲染对象分离

Three.js Object3D 是渲染/运行时载体，不是唯一权威世界数据。应逐步建立可序列化的 World Document / World Object 数据结构，包含对象身份、实例变换、状态、绑定、交互和空间关系；渲染对象可从数据恢复。不要把完整业务状态只塞在 Mesh.userData 或仅依赖 Object3D.toJSON()。

### 3.8 物理、空间、导航

- 视觉网格与碰撞表示分离；优先使用简单碰撞体。
- 明确可行走地面、阻挡体、门/楼梯/电梯等空间连接。
- 空间层级预留 World → Zone → Building → Floor → Room。
- MVP 先保证基础地面移动、碰撞和对象交互范围；复杂导航后续扩展。

### 3.9 生命周期、持久化与版本

- 对象生命周期至少覆盖创建、加载、启用/禁用、更新/替换、删除、卸载、恢复。
- 模型替换/AI 修改时，稳定对象 ID、状态、Transform 和关系应按策略保留；不能依赖 Mesh 名称。
- 存档应有版本号与迁移策略，逐步保存世界对象、Transform、环境定义/值、对象状态、交互配置、环境绑定和空间关系。
- 本地存储可作为 MVP 持久化方式；后续再评估服务端同步。
- 旧版 v1 存档需要迁移到后续 World Document 版本，不能直接丢弃。

### 3.10 性能与安全

- 模型代码隔离执行；禁止 AI 生成源码直接在主线程执行。
- 对象资源必须可释放；删除/替换模型要处理 Geometry、Material、Texture、监听器和运行时订阅的生命周期。
- 后续按需引入 LOD、视锥剔除、实例化渲染、区域加载、阴影分级和非活动区域降频。
- AI 生成的数据需要基础结构/资源边界处理，但不要建立会阻止合理新部件和新参数的僵化业务白名单。

### 3.11 AI 模型能力与环境绑定协议

模型生成和模型能力不是同一件事。模型定义负责描述几何、材质和部件；能力声明负责描述模型/部件能响应哪些环境变量、提供哪些控制入口；Runtime 负责把环境值映射为实际运行效果。

- AI 程序化模型模块应导出 `environmentBindings` 数据数组；Worker 将其复制到模型根节点的序列化元数据中。模型没有环境响应能力时导出空数组。
- 每条绑定使用稳定的 `targetPartId` 指向真实部件的 `userData.componentId`，并声明 `variable`、`property`、默认值及开/关映射。Mesh 名称、显示名称不能作为关联主键。
- 环境变量采用命名空间标识，例如 `lighting.artificial.enabled`。变量定义和值属于 Environment System；模型只声明订阅关系，不拥有全局环境值。
- Runtime 只消费数据声明，不执行 AI 返回的任意行为代码。第一阶段支持 `visible`、`intensity`、`emissiveIntensity` 三种受控渲染属性；新增运行属性需由 Runtime 明确实现。
- 全局环境值默认作用于所有已注册绑定；对象级 `environmentOverrides` 对同名变量具有更高优先级。局部显式 false 必须覆盖全局 true；清除局部覆盖后恢复继承。
- 新模型在加入沙盒时自动注册并应用当前环境值；环境变化时 Runtime 更新所有已注册模型；保存/恢复时保留绑定和局部覆盖。
- AI 微调必须接收当前模型源码、部件元数据和已有环境绑定。用户可用自然语言要求旧模型接入新能力；AI 优先复用现有部件，只在缺少必要组件时做最小结构增量，并保留无关几何、模型身份、Transform、对象状态和局部覆盖。
- 绑定是开放的数据协议，不按教学楼、路灯、树木等对象类别建立业务白名单。Runtime 属性映射属于执行安全边界，不等同于限制模型类别或部件命名。
- 旧模型如果保留了可编辑程序化源码，可以通过 AI 微调升级；没有可编辑源码的模型不能承诺仅靠一句话无损升级，需要先重建可编辑定义或进行人工/AI 结构转换。

### 3.12 模型固有参数、世界环境变量与运行状态（三层数据边界）

必须将模型自身的定义、沙盒提供的外部环境，以及模型实例运行时发生的变化分开存储。三者有关联，但不能混成一个参数集合。

#### A. 模型固有定义（Model Definition）

模型固有定义由 AI 在建模/重建时声明，随模型定义保存。它描述“这个模型是什么、具备什么结构和能力、如何参与世界”，不是某一时刻的世界状态。

包括：

- **几何与材质定义**：模型部件、尺寸、材质、层级和稳定部件 ID。
- **可编辑参数（Model Parameters）**：如宽度、高度、深度、楼层数、颜色、房间数量等。参数定义与当前参数值分离；AI 可按用户指令动态增加、修改或删除，不建立固定业务参数白名单。
- **空间/物理属性（Spatial Properties）**：碰撞体、阻挡/可穿越区域、入口/出口、可进入声明、空间连接和内部空间结构。是否可穿越应精确到部件或区域；不能把“建筑可进入”解释为整栋建筑无碰撞。
- **环境响应声明（Environment Bindings）**：模型/部件订阅哪些世界环境变量，以及变量如何影响其表现。声明属于模型固有定义，环境变量的实际值不属于模型。
- **交互能力声明（Interaction Capabilities）**：模型提供哪些交互入口、动作、条件和目标关系。例如开关关联灯具、门提供 open/close/enter。它描述可执行能力，不代表当前动作状态。
- **内部空间结构（Interior Definition）**：模型确实包含内部空间时，才声明楼层、房间、走廊、楼梯、门洞和空间连接；普通模型无需伪造这些字段。

以上能力按模型实际情况选择性声明。字段缺失表示模型未声明该能力，不要求每个模型都具有碰撞、内部空间、灯具或交互入口。AI 可通过自然语言增量修改这些定义；修改应尽量保留无关几何、稳定 ID 和实例状态。

#### B. 世界环境变量（World Environment）

世界环境由沙盒统一管理，是模型之外的输入，例如时间/太阳、天气/降雨、风向/风速、重力和全局人工照明。

- 环境变量的定义、启用开关、参数值和全局/局部作用范围归 Environment System 管理。
- 模型通过 Environment Bindings 选择性订阅环境变量；模型不能自行拥有或覆盖全局环境真值。
- 全局环境值可以被区域/对象级显式覆盖；局部覆盖优先级由 Environment Runtime 统一解释。
- 模型没有声明某项环境绑定时，不应因为环境变量存在就自动产生效果。

#### C. 模型实例运行状态（Model Instance State）

运行状态描述“这个实例此刻是什么状态”，由玩家交互、模拟或世界事件改变，并随世界存档保存。例如：

- 灯当前开/关、门当前开/关、窗户当前开/关。
- 电梯当前楼层、设备运行/停止、房间当前占用状态。
- 运行时临时启用/禁用的设备状态。

运行状态不能反向覆盖模型固有定义。例如灯具当前关闭，不代表模型定义中的灯具能力或环境绑定被删除；门当前打开，也不代表门洞/碰撞结构被永久改写。

#### 三层数据流

`Model Definition` 声明结构和能力 → `World Environment` 提供外部变量 → `Model Runtime` 根据绑定和当前状态产生实际表现。

玩家交互通过 Interaction/State Runtime 修改实例状态，再由 Runtime 更新视觉、碰撞或设备表现；AI 对话修改的是模型定义/能力声明，除非用户明确要求改变某个实例当前状态。

#### 建议的数据组织（协议方向，不要求一次性创建同名文件）

```js
{
  modelDefinition: {
    version: 1,
    parameters: [],
    capabilities: {
      spatial: {},
      interior: {},
      environmentBindings: [],
      interactions: []
    }
  },
  instance: {
    id: "stable-instance-id",
    transform: {},
    state: {}
  },
  worldEnvironment: {
    values: {}
  }
}
```

这是职责边界示意，不是本轮已经落地的运行时 Schema。实际协议应允许 capabilities 下的能力段缺省，并为未来版本迁移保留 version。

#### 实施约束

- 不按建筑、树、灯具等模型类别写死能力模板；能力由 AI 根据实际模型结构声明。
- 不把“可穿越”简化成根对象 boolean。应支持部件级碰撞/通行描述，以及入口/通道等空间区域。
- 不把环境绑定与环境变量值放在同一数据源；绑定是模型定义，值由世界环境管理。
- 不把灯具 enabled、门 open 等动态值存入模型定义；它们属于实例运行状态。
- Runtime 只执行已实现的受控能力协议，不执行 AI 任意 JavaScript。未知能力声明可保存在模型定义中，但未有对应 Runtime 时不得伪称已生效；应记录为待支持能力，而不是因模型类别未知就拒绝整个模型。
- 老模型若保留可编辑程序化源码，可由 AI 增量补充能力声明；只有静态图像或不可编辑网格时，无法保证无损补齐隐藏内部结构。

### 3.13 Model Capability Manifest v1（第一阶段数据协议）

程序化模型以 `modelCapabilityManifest` 作为模型固有能力的主声明。Manifest 是模型定义的一部分，不包含世界环境当前值，也不包含某个实例此刻的开关/门状态。

#### 协议结构

```js
export const modelCapabilityManifest = {
  version: 1,
  parameters: [
    // 模型固有的可编辑参数定义；与当前参数值分离
  ],
  capabilities: {
    // 按实际模型选择性声明；不存在的能力段直接省略
    spatial: {
      // 部件/区域级 colliders、traversalZones、enterable 等声明
    },
    interior: {
      // floors、spaces、connections 等室内结构声明
    },
    environmentBindings: [
      // 模型/部件对世界环境变量的订阅与响应声明
    ],
    interactions: [
      // 交互入口、动作、稳定目标关系等数据声明
    ]
  }
};
```

以上是结构约定。除 `version`、`parameters`、`capabilities` 外，Manifest 和 capability section 可扩展；未实现的能力声明可以保存和往返传递，但 Runtime 不得假装已经执行。

#### 与现有字段的兼容规则

- `modelCapabilityManifest.parameters` 是模型参数定义；现有命名导出 `modelParameters` 暂作为兼容别名。当前参数值仍由现有 `proceduralModelParameterValues` 保存，不把实例当前值塞进能力定义。
- `modelCapabilityManifest.capabilities.environmentBindings` 是主声明；现有命名导出 `environmentBindings` 和根节点 `userData.proceduralModelEnvironmentBindings` 暂作为 Runtime 兼容别名。第一阶段 Runtime 仍从兼容字段读取人工灯光绑定。
- `modelParts` 仍是部件选择/编辑 UI 的兼容元数据，不等同于空间、碰撞或交互能力。
- Worker 读取 AI 模块的 Manifest；旧模型没有 Manifest 时，根据旧 `modelParameters` / `environmentBindings` 合成 v1 兼容 Manifest。
- Worker 将 Manifest 保存到根节点 `userData.proceduralModelCapabilityManifest`。现有 Object3D JSON 存档会随模型 userData 保存该声明。
- AI 微调请求携带当前 Manifest；AI 返回完整更新 Manifest。服务端兼容旧模型：若 AI 未返回 Manifest，则沿用旧 Manifest/旧绑定并构造兼容结果。
- 模型替换和撤销历史保留 Manifest；Manifest 中的环境绑定与旧字段必须同步，避免 Runtime 读取到过期绑定。

#### 安全与演进边界

- Manifest 是纯数据，不允许函数、可执行源码、eval 字符串或任意运行时代码。
- 第一阶段不对未知 capability key 做业务白名单校验；Worker/页面保留未知声明字段，供后续 Runtime 版本解释。
- 当前没有 Spatial/Interior/通用 Interaction Manifest Runtime；这些字段即使已保存，也只代表模型声明，不代表碰撞、室内导航或交互已生效。
- 后续版本通过 `version` 演进，并以显式迁移处理旧字段；不要在这一阶段一次性迁移全部 World Document。

### 3.14 Spatial Runtime v1 — 部件级地面移动碰撞

第一阶段只实现可验证的地面移动阻挡，不把 Manifest 中所有空间声明都视为已支持。

#### 当前执行协议

`modelCapabilityManifest.capabilities.spatial.colliders` 可声明部件级碰撞体：

```js
{
  id: "wall-collider",
  targetPartId: "wall-part",
  shape: "box",
  center: { x: 0, y: 1, z: 0 },
  size: { x: 4, y: 2, z: 0.3 },
  blocksMovement: true,
  enabled: true
}
```

- `targetPartId` 必须对应模型部件的稳定 `userData.componentId`。
- `center` / `size` 使用目标部件局部坐标；Runtime 根据部件世界矩阵转换为世界空间 AABB。
- 当前玩家控制器在 XZ 平面移动；只注册与地面站立高度区间相交的碰撞体。
- 仅 `shape: "box"` 且未显式禁用、未显式设为非阻挡的声明参与当前 Runtime。
- 碰撞体按模型实例 ID 归属；模型移动/旋转/缩放、替换和删除时更新或清理对应障碍。
- 门洞通过墙体分段/独立部件表达：墙体有碰撞声明，门洞本身不生成碰撞体。不得用整栋建筑根对象碰撞体封死入口，也不得用根对象可穿透来绕过墙体碰撞。
- 缺少 spatial.colliders 的旧模型继续保持原有行为，不自动推断碰撞。

#### 当前未实现

- 圆形/胶囊/多边形/网格碰撞体。
- traversalZones、可行走面、门/楼梯/电梯连接、室内楼层导航。
- 动态门开关对碰撞体启停的状态绑定。
- 垂直方向完整胶囊体物理、重力、跳跃和刚体模拟。

以上字段即使被 Manifest 保存，也不代表当前 Runtime 已执行。

### 3.15 Spatial Runtime v2 — 门洞与状态驱动门扇（当前增量）

本阶段在 v1 地面 Box Collider 基础上增加门扇状态联动，不将声明式 interior/portal 数据误认为已经支持室内导航。

#### 已实现的数据与执行约定

- 墙体必须按门洞结构拆分为独立实体段/碰撞段；门洞净空不得存在墙体 blocker。门洞本身不是一个需要“关闭阻挡”的 collider。
- 每个 collider 使用模型内稳定唯一的 `id`，`targetPartId` 指向真实的 `userData.componentId`。旧模型缺少 collider id 时继续兼容旧回退规则，但新生成/微调结果必须输出唯一 ID。
- 普通静态 collider 继续使用 `blocksMovement`。
- 可开合门扇可使用 `stateCondition: { key, equals, defaultValue }`。Runtime 从模型实例 `worldState[key]` 读取状态；缺少状态时使用声明的 defaultValue。条件不满足时不注册该门扇碰撞体。
- 门扇部件可使用 `userData.stateBinding = { key, property: "rotationY", enabledValue, disabledValue }`，由 World State Runtime 驱动铰链旋转。门扇部件局部原点应位于铰链，几何与 collider 均使用该部件局部坐标。
- `setSandboxModelState` 更新实例状态后同步刷新该模型的空间碰撞。用户明确的部件级 capability override 优先于 stateCondition。
- 门状态属于 Model Instance State，不能写回 Manifest；碰撞定义仍属于 Model Definition。


#### Spatial Runtime v2 — 玩家近距离门扇交互增量

- `findNearestSandboxInteraction` 遍历沙盒模型的部件级交互声明，按部件世界坐标、交互点和半径选出最近目标。
- 部件通过数据声明 `userData.interactionConfig = { action: "toggle-state", stateKey: "doorOpen", radius, prompt }` 提供交互入口；Runtime 不执行模型提供的函数或脚本。
- 玩家靠近目标后显示声明的 prompt，按 E 向页面发出模型 ID、部件 ID 和受控配置；页面只执行当前支持的 `toggle-state`，默认写回所属模型实例的 `worldState`。
- 状态更新继续经过 `setSandboxModelState`，驱动门扇 `rotationY` 绑定和碰撞障碍刷新；实例状态由现有 Object3D 存档路径保存。
- 模型部件未声明交互时保留原有模型根级交互回退，避免破坏灯具演示等旧交互。
- 当前只在 RPG 沙盒玩家循环启用；尚未建设通用 Interaction Registry、条件表达式、权限系统、动作队列或复杂交互类型。

#### 当前执行边界

- 已支持：Box 地面移动碰撞、门扇 boolean 状态条件、`rotationY` 状态绑定、状态变化后的碰撞刷新。
- 仍未支持：自动几何切割/自动检测门洞、非 Box 碰撞、Portal/Traversal Zone、室内可行走区域、楼层/楼梯/电梯导航。
- AI Prompt 负责生成分段几何和声明；Runtime 不会从一个完整墙体 Mesh 中自动挖洞。模型若未拆分墙体或碰撞体跨越门洞，仍会挡住玩家。
- 已接入最小玩家近距离交互：沙盒在玩家半径内查找模型部件的 `userData.interactionConfig`，按 E 触发受控 `toggle-state`；部件动作默认更新所属模型实例状态，无需把同模型门扇的 targetId 硬编码进 AI 资产。无部件级声明时保留旧的模型根级交互回退。当前只在 RPG 沙盒场景启用，尚不是通用 Interaction Registry。


### 3.16 通用几何一致性与参数能力绑定（当前推进约束）

本节是所有模型生成、微调和 Runtime 的通用规则，不得按房屋、屋顶、烟囱、树木、车辆、家具等类别增加专用修补器或参数白名单。

#### 通用几何诊断（第一版实现边界）

- 程序化模型在独立 Worker 中创建完成后，Runtime 对实际 THREE.Mesh / BufferGeometry 采集诊断快照，并随模型根节点 userData 序列化保存。
- 每个 Mesh 记录稳定 componentId（若存在）、顶点数量、局部边界和世界边界；诊断包括缺失/空 position attribute、非有限顶点、非有限世界变换、非有限世界边界和整体退化边界。
- 单一维度为零的平面/薄片不因此判错；只有所有边界维度都近似为零时才记录退化候选。
- 诊断只作为可追溯证据，不阻止模型进入沙盒、不自动修改几何，也不将 AABB 相交解释为缺陷。当前不做完整网格拓扑检查、接触/覆盖证明或自动修复。
- AI 微调请求可携带当前诊断快照，后端限制传入上下文大小；AI 必须区分确定性数值异常与启发式空间线索，局部修复时保留无关部件。
- 诊断规则不依赖对象类别、Mesh.name 或中文部件名称。没有稳定 componentId 的 Mesh 仍记录几何数据，但其诊断目标 ID 为空，后续需要 AI/生成器补齐稳定 ID。

#### 几何一致性

- 生成和微调必须统一根坐标系，并正确计算父子局部变换、世界变换和几何边界。
- AI 应基于实际几何与空间关系检查连接/接触、表面覆盖、可见缝隙、异常裁切、无依据悬空、部件脱离及超出合理装配范围等问题。
- 几何交叠、间隙、开口、悬挑、空腔可能是设计意图；不能把所有 AABB 重叠或部件不接触都判为错误。参考图与用户明确要求优先。
- 检查与修复不依赖 Mesh.name、部件中文名称或对象类别；使用稳定组件 ID、变换矩阵、几何边界和实际拓扑关系。
- 修复应局部化，保留无关几何、稳定 ID、用户参数、实例 Transform 和状态。通用诊断是证据，不应把启发式边界检查误报为确定性几何缺陷。
- 不为单一模型添加永久特例；遇到新问题应提炼为可跨对象复用的空间关系或几何质量规则。

#### 动态参数与能力绑定

- 模型参数继续由 AI 按实际模型动态声明；UI 依据元数据呈现，不增加固定对象类别参数目录。
- 参数可以通过声明式 `bindings` 指向稳定的 capabilityId 和属性。当前第一项 Runtime 支持：参数定义中的 `bindings: [{ capabilityId: "spatial.collider.<id>.blocksMovement", property: "blocksMovement" }]`。
- 参数绑定只影响被引用的具体能力目标，不得隐式关闭整个模型或所有碰撞体。
- 优先级：显式用户 capability override > 参数绑定值 > 模型能力定义/状态条件。用户覆盖不能被参数变化或后续 AI 编辑静默覆盖。
- 当前已实现参数驱动部件 Box Collider 的移动阻挡开关；`enterable`、室内视角、室内导航等能力即使可以声明和保存，在相应 Runtime 完成前仍标记为未执行。
- 新增其他参数绑定属性时，必须同时实现对应通用 Runtime adapter 和测试；仅在 Prompt 中声明不算功能接通。

#### 本轮后续推进顺序

1. 通用几何一致性生成/微调规则与可追溯诊断；不做模型类别专用修补器。
2. 参数元数据到通用能力目标的绑定；先完成已实现的部件级移动阻挡控制。
3. 通用室内空间、入口连接和室内视角生命周期；不依赖校园原有建筑楼层数据。
4. 每一阶段以真实端到端用例验证，不提前铺设大型通用框架。

### 3.14 通用对象能力：AI 推理、用户控制与 Runtime 执行

本节适用于**所有世界对象及其部件/区域**，不是墙体碰撞专用协议，也不按建筑、树木、家具、设备等对象类别建立固定能力模板。对象可以是实体模型、部件、空间区域、环境实体或运行设备；能力由对象实际结构、用户意图和世界上下文决定。

#### 核心职责分离

1. **AI Capability Reasoning（推理层）**：读取模型几何/部件层级、已有能力、用户指令及必要的世界上下文，自主推断对象具备的能力、约束和依赖关系；用户未明确提出的部分由 AI 自动补全，不逐项请求确认。推断结果进入自动解析流程，但在 Runtime 编译/执行前仍不代表已生效。
2. **User Capability Control（控制层）**：用户通过自然语言、参数化控制和对象/部件/区域局部覆盖随时调整结果；用户本轮明确指令优先于已保存覆盖、模型定义和 AI 推断。AI 后续编辑不得静默覆盖用户明确设置。
3. **Capability Resolver / Compiler（解析编译层）**：合并模型定义、用户覆盖和运行时上下文，检查引用、冲突和依赖，再将可执行部分编译为 Runtime 能消费的声明。
4. **Capability Runtime（执行层）**：只执行当前确实实现且通过编译的能力；未实现或无法解析的能力保留在数据中并报告状态，不得显示为已生效。
5. **Diagnostics / Repair Loop（诊断修复层）**：Runtime 回报缺失部件、无效引用、几何冲突、不支持的执行器和执行失败；AI 可基于诊断提出局部修复，用户仍可审阅和控制。

#### 能力覆盖范围

能力不是预先封闭的枚举。AI 应根据实际对象判断是否需要声明，例如但不限于：

- 空间与物理：阻挡、穿越、站立、承载、移动、可进入、碰撞、破坏、附着、连接。
- 结构与拓扑：内部区域、房间、楼层、入口、通道、楼梯、电梯、邻接和包含关系。
- 环境响应：受时间、光照、天气、风、温度或其他环境变量影响。
- 交互与状态：可点击、可开关、可开合、可拾取、可放置、可使用、可激活，以及对应状态和状态转换。
- 运动与行为：摆动、旋转、流动、开合、周期行为、触发条件和约束。
- 视觉与音频：透明度、发光、材质变化、动画、声音及其触发条件。
- 资源与生命周期：启用/禁用、显示/隐藏、生成、销毁、替换和依赖关系。

上述清单用于说明适用面，不是必须字段清单或 Runtime 支持承诺。能力可以按模型、部件、区域或实例定义；不同能力可以有依赖、互斥、条件和作用范围。

#### 三类数据必须分开

- **AI 推断记录（Inference）**：记录 AI 提议的能力内容、目标范围、来源、置信度、依据/证据、生成时间及推断状态。置信度是供用户判断的元数据，不是 Runtime 自动启用能力的授权。
- **用户控制覆盖（Override）**：独立保存用户明确接受、修改、禁用或补充的内容，支持全对象、指定部件、指定区域和单项属性范围。清除覆盖后回到推断/定义结果；覆盖不能被后续 AI 自动重写。
- **Runtime 执行结果（Execution）**：记录编译结果、实际启用的执行器、诊断、支持状态和运行时句柄/派生数据。执行结果是派生数据，不应反向污染模型定义。

解析优先级：**用户本轮明确指令 > 已保存的用户覆盖 > 模型定义 > AI 最新推断 > Runtime 安全默认值**。AI 推断默认自动进入解析/编译流程，不设置逐项人工确认或置信度审批门槛；置信度只用于诊断和追溯，不决定是否需要用户批准。

#### 开放数据协议方向

Manifest 继续作为模型固有定义的入口，但不把所有职责塞进一个扁平 capabilities 字段。可逐步演进为以下职责分区（示意，不是要求一次性实现固定 schema）：

```js
{
  version: 2,
  parameters: [],
  capabilities: {
    // AI 对模型固有能力的声明；允许任意扩展命名空间与字段
  },
  reasoning: {
    // AI 推断记录：proposals、confidence、evidence、source、status
  },
  userOverrides: {
    // 用户接受/拒绝/修改的局部控制记录
  }
}
```

更稳妥的最终持久化边界是将 inference、userOverrides 和 runtime diagnostics 作为独立文档/记录保存，并通过稳定的 modelId、partId、regionId 和 capabilityId 关联；上面的嵌套结构只用于表达职责，不要求它们最终都物理存放在 Manifest 内。实例运行状态仍属于 Model Instance State，不能混入模型固有定义。

协议必须满足：
- 任意能力数据可扩展、可往返保存；不通过对象类别、部件名称或能力名称白名单限制 AI 表达。
- 所有目标使用稳定 ID 与明确 scope；显示名称和 Mesh.name 不作为主键。
- 推断来源、用户覆盖、编译结果和实例状态有不同来源标记，不能互相覆盖。
- 局部修改只影响指定目标及必要依赖，尽量保留无关几何、ID、Transform、实例状态和已有用户覆盖。
- 未知能力字段必须保留；没有 Runtime 执行器时标记 unsupported/uncompiled，而不是丢弃或假装生效。
- Manifest 只允许声明式数据，不包含任意函数、JS 源码、eval 字符串或可执行脚本。

#### 从意图到执行的标准链路

`Model Geometry / Context + User Intent → AI Capability Inference → Capability Resolver（用户指令/覆盖优先）→ Spatial/Behavior/Environment Compiler → Runtime Adapter → Diagnostics → AI Repair / Incremental Update`

编译器不是另一个模型类别白名单。它负责把通用能力意图映射到已实现的执行器；执行器能力可以逐步增加，但不能限制 AI 保存和表达未来能力。

例如，“这个玻璃隔断允许玩家穿过，但仍然显示玻璃材质”应被解释为对空间阻挡能力的局部覆盖，而不是删除玻璃模型；“树冠随风摆动”应分别涉及环境订阅、运动行为和部件范围；“按下按钮后电梯到三楼”涉及交互入口、状态转换、空间连接和运行时反馈。系统不应要求用户理解这些底层结构才可提出要求。

#### Capability Control 数据协议第一阶段实现约定

第一阶段先建立不依赖 Three.js 的纯数据解析层，避免将推断、覆盖和执行耦合进当前碰撞代码：

- `capabilityControlDocument` 暂采用独立文档结构：`version`、`inference.proposals[]`、`overrides[]`、`diagnostics[]`。未知顶层字段和记录字段必须原样保留。该文档随模型根节点 `userData.proceduralModelCapabilityControlDocument` 进入 Object3D JSON，因此随模型复制/保存/恢复传递；Worker 根据 AI 输出的 Manifest capability namespaces 自动构建 inference proposals，模型替换时保留已有 overrides/diagnostics。
- 每条记录以 `capabilityId` 和 scope 定位；scope 可指向 model、part、region 或未来的其他稳定目标。能力 ID 不经过白名单校验。
- AI 推断记录携带 source、confidence、evidence、scope 和 value 等可追溯信息；不要求用户逐项确认。AI 推断默认自动进入解析结果，旧版 status=proposed 仅作为兼容输入，不再代表等待人工审批。
- 用户明确指令与已保存用户覆盖独立记录，支持 set、disable、reject 等控制语义；AI 后续推断/编辑不得静默覆盖用户明确设置。
- 解析优先级：Runtime fallback < AI inference < model definition < saved user override < current-turn explicit user instruction。当前纯数据 resolver 支持前四层；当前轮指令应在调用 resolver 前转成最高优先级的临时 override。
- AI 未提及某项能力时，由 AI 根据模型结构和上下文自主推断；若明确无法判断，应采用保守默认值并保留推断依据/不确定性，而不是要求用户确认。
- 解析器只产出解析记录，不调用 Three.js、不执行代码、不宣称 Runtime 已生效。后续需区分 resolved、compiled、applied，并由 Runtime adapter 确认执行后才能标记 applied。
- 显式 enabled=false、disable 或 reject 可关闭对应能力；AI 推断默认 enabled=true，但记录自身明确声明 enabled=false 时必须保留该值。
- Capability Control 文档已接入模型 Worker、模型根节点 userData、编辑替换/撤销及 Object3D JSON 保存恢复；该接入目前负责推断记录派生和文档生命周期，不代表 overrides 已有用户编辑 UI，也不代表 resolved capabilities 已接入各 Runtime。

#### 当前 Spatial Runtime 的定位

当前 `modelCapabilityManifest.capabilities.spatial.colliders` 和 `collectModelMovementObstacles` 是第一个底层执行切片：把明确声明的 box blocker 转换为 XZ 移动障碍。模型编辑器已提供能力概览，并允许用户对指定部件的 box collider 设置 `blocksMovement` 覆盖；Runtime 通过 Capability Resolver 合并模型定义与用户覆盖后重建障碍。该闭环不等于通用能力推理，也没有自动理解所有模型的穿越、承载、进入或连接能力。

能力面板按 Manifest 的能力命名空间展示能力声明，并标注当前 Runtime 接入范围。当前只有空间 box movement blocker 提供实际控制；其他能力只展示“未接入 Runtime”，不提供伪开关。用户覆盖写入独立的 `capabilityControlDocument.overrides`，不修改 AI 原始 Manifest；该文档随 Object3D JSON 存档、恢复和模型微调生命周期保留。

当前 Runtime 只执行 box movement blockers；其他空间/行为能力必须如实标记为未执行。后续增加能力时，沿用“声明 → 用户覆盖 → Resolver → 对应 Runtime adapter → 实际效果”的闭环，不按模型类别建立固定白名单。

### 3.15 统一模型生成与编辑工作台

新建模型与已有模型的二次编辑必须复用同一个工作台组件，不再建设互相独立的生成页面和编辑页面。

#### 交互状态

- **创建/生成中**：从沙盒创建入口打开工作台。左侧为 Three.js 预览视口，右侧显示 AI 请求与 Worker 的真实阶段事件、阶段说明和失败信息；不展示伪造的百分比。
- **创建/编辑中**：模型构建完成后，工作台继续保持打开。左侧显示实际 Three.js 模型预览；右侧切换到模型参数、能力/部件信息和 AI 对话编辑。
- **已有模型编辑**：沙盒中双击带有可编辑程序化源码的模型，打开同一个工作台并加载该模型。
- **保存新模型**：生成草稿在保存前不加入世界对象列表；用户点击“保存并加入沙盒”后创建世界实例并写入当前沙盒存档。若存档写入失败，工作台保持打开并允许重试，且明确提示模型当前仅存在于本次运行内存。
- **保存已有模型**：编辑完成后通过工作台保存入口写入沙盒存档；模型仍是原实例，不创建重复实例。

#### 数据与生命周期约束

- 工作台预览来自当前模型 Object3D 数据，不通过第二次生成构造一套不同的预览模型。
- 新模型在保存前作为草稿存在于编辑状态，不参与沙盒碰撞、玩家交互或世界存档；取消创建不得留下世界实例。
- 草稿参数修改和 AI 二次编辑仍使用隔离 Worker 构建模型；失败时保留上一个有效草稿版本。
- 已有模型编辑沿用现有模型替换路径，保留模型定义元数据、用户能力覆盖、对象运行状态和实例身份；保存不创建新实例。
- 生成源码在服务端生成后仍只能在独立 Worker 中执行；Worker 仅回传 Object3D 序列化数据和阶段事件，不能直接访问主沙盒场景。
- Worker 当前只能报告真实阶段边界（源码检查、模块加载、模型构建、能力元数据整理、几何诊断、序列化）。若 AI 输出的 createModel 是同步函数，构建函数内部没有可观察的子阶段；UI 不得把这些阶段伪装成精确百分比或模型部件逐项完成进度。AI 分块生成阶段则展示真实组件名称、序号、等待状态和源码接收状态；所有组件完成后才显示最终预览。
- 视觉 AI 截图复核、自动修复和多轮质量闭环属于后续阶段；本工作台第一阶段先完成统一入口、实际预览、真实进度、参数/对话编辑和保存生命周期。

#### 第一阶段验收标准

1. 从沙盒发起生成时，统一工作台立即打开；生成期间右侧能显示后端请求与 Worker 实际阶段。
2. Worker 执行期间主页面保持可交互；生成源码不在主线程执行。
3. 模型构建完成后，左侧出现实际 Three.js 预览，右侧切换为已有模型编辑面板。
4. 参数修改、AI 对话修改、部件选择仍可复用现有编辑能力。
5. 新模型保存前不出现在沙盒；保存后只创建一个实例并可被选择、移动和存档。
6. 双击该实例再次打开同一个工作台；编辑保存后更新原实例，不产生重复实例。
7. 生成失败或取消创建不污染沙盒；已有模型编辑失败时原有效模型保留。


### 3.16 增量式程序化模型构建协议（第一阶段：协议与依赖排序）

当前程序化模型生成接口一次请求返回完整 `generatedCode`，Worker 再一次性执行 `createModel` 并回传完整 Object3D。AI 在 Prompt 中被要求组织稳定部件层级，但这不等于服务端已经逐部件生成或实时预览。

后续生成链路采用按复杂度选择的混合策略：

- **简单模型**：保留当前 one-shot 完整模型生成，避免额外请求和拆分开销。
- **复杂模型**：先生成整体 ModelBuildPlan，再按显式依赖分批生成 ComponentChunk；组件源码在生成阶段仅暂存，不逐块执行或展示，全部组件完成后再一次性进入隔离 Worker 构建完整模型。
- **局部编辑**：以稳定 componentId 定位修改范围，只重建目标组件及其依赖/受影响组件；未受影响组件和用户状态继续保留。

#### 协议 v1

- `ModelBuildPlan` 描述统一模型 ID、名称、Y-up 场景坐标系、组件稳定 ID、父级关系、依赖关系及可选边界/用途元数据。
- `ModelComponentChunk` 以 `componentId` 关联独立组件源码；源码仍属于不可信输入，只允许在专用 Worker 执行。
- `ModelBuildEvent` 统一表达 plan、组件开始/完成、装配、诊断、完成和错误事件，为后续 SSE/NDJSON 传输提供事件载荷。
- 组件名称、用途、类别和未知元数据保持开放；协议不内置建筑、树木、车辆、家具等类别白名单。
- 所有组件共享同一 ModelBuildPlan、坐标系和依赖图；不得把多个无上下文的独立生成结果简单拼接。
- 依赖排序只依据稳定 ID、parentId 和 dependsOn，不推断几何语义，也不以 Mesh.name 作为标识。
- 单组件失败时保留已完成组件预览并允许重试；装配失败不得覆盖上一个有效模型版本。

#### 第一阶段实际交付与边界

- 已新增 `server/src/modules/assets/procedural-model-build.protocol.ts`，定义协议类型及通用依赖拓扑排序函数。
- 已新增协议单元测试，覆盖开放组件语义、父子依赖、显式依赖、重复 ID、缺失依赖和循环依赖。
- 本阶段**尚未**改造现有生成 API、AI Prompt、SSE/NDJSON 响应、前端工作台或 Worker 分块预览；当前线上链路仍是单次返回完整源码。
- 不将普通 token 流误认为组件完成事件；只有完整 ComponentChunk 到达且可独立构建后，才允许更新对应预览。
- 流式能力必须在核实当前部署的 OpenAI-compatible 服务支持情况后接入；不能仅凭接口兼容地址推断支持 SSE。

### 3.16.1 增量构建协议边界补充（2026-11-07）

- 组件 `parentId` 和 `dependsOn` 均为有向依赖边；直接自依赖与多节点循环都属于无效构建计划，必须在生成组件源码前失败。
- 依赖排序只处理 ID 和依赖关系，不解释组件名称、类别或几何语义。
- 当前协议仅定义数据结构与排序；后端仍是一次性 `/chat/completions` JSON 响应，尚未接入 plan/chunk 多轮请求、SSE/NDJSON 事件传输、Worker 分块执行或逐块预览。不得将协议存在描述为实时构建已完成。

### 3.17 增量模型生成与 NDJSON 预览（历史实现，当前新建流程已停用）

- 曾实现按模型复杂度选择 `single/components` 的增量构建流程，并通过 NDJSON 推送组件级进度。
- 该方案在组件高度耦合的整体模型上会引入规划请求和多次串行模型请求；组件数量增加会线性增加网络往返，任一组件超时可能导致整次生成失败。
- 当前新建模型流程已不再调用 ModelBuildPlan / ComponentChunk，不再逐组件生成；相关协议文件暂时保留为历史/后续实验能力，不属于当前默认生成路径。
- 前端不再展示组件序号、组件名称或组件源码接收进度；只展示完整生成、有限重试、Worker 构建和完成/失败等真实阶段。

### 3.18 规划响应结构化输出（历史实现，当前新建流程不再需要）

- 原增量流程曾对规划请求启用 OpenAI-compatible JSON Object response format。
- 当前新建模型流程不再发起独立规划请求，因此不再依赖规划 JSON、ModelBuildPlan 解析或 `response_format: { type: 'json_object' }`。
- 完整模型请求直接返回 JavaScript ES module 源码；源码仍需检查工厂导出并在隔离 Worker 中执行。

### 3.19 整体模型一次性生成与请求级重试（当前默认策略）

- 新建模型以完整对象为生成单位。AI 在一次模型请求中理解整体结构、部件层级、空间关系和能力声明，并输出一个完整 `createModel(THREE, params = {})` 工厂。
- 不再先请求 AI 做策略规划，不再根据复杂度切换 `single/components`，不再发起逐组件 ComponentChunk 请求。部件之间的引用关系由同一次生成上下文内部处理。
- 服务端复用既有完整模型 Prompt 和 `generateProceduralObjectFromPrompt`，通过 NDJSON 仅推送阶段事件；NDJSON 是进度传输，不代表模型服务 token 级流式输出。
- Worker 仍然只在源码完整返回后执行一次，创建完整 Object3D 并执行现有几何诊断；模型能力 Manifest、参数、部件元数据和环境绑定仍沿用既有导出协议。
- 对网络连接异常、响应 JSON 不完整，以及 HTTP 408/425/429/5xx 实施最多 3 次总尝试（最多 2 次重试）；单次请求超时最多重试 1 次，避免长时间重复等待。HTTP 400/402 等非暂时性错误不重试。429 优先遵守 Retry-After，等待时间设有上限。
- 每次重试必须通过 NDJSON 阶段事件显示真实原因和尝试次数；不模拟百分比，不显示组件级进度。
- 记录生成请求总耗时、尝试次数和源码字节数，便于后续判断模型服务响应时间是否仍是瓶颈。
- AI 后续微调仍沿用独立的局部/整体编辑接口；本决策不意味着首次生成失败后自动执行视觉修复。视觉审核和局部修复仍作为后续独立能力。
- 不改变 Worker 隔离边界，不执行 AI 源码于 NestJS 或主线程，不修改 `main`。

#### 验收标准

1. 新建一个复杂模型，后端只发起一次成功的完整模型生成请求；正常情况下不再出现 planning 或 component-start/component-complete 事件。
2. 一次模型请求超时或遇到暂时性服务错误时，最多自动重试 2 次；402 不重试。
3. 前端只显示整体生成、重试、Worker 构建和预览完成等阶段，不出现“生成组件 x/y”。
4. 收到完整源码后只调用一次隔离 Worker 构建；Worker 成功前不显示半成品。
5. 记录并可从日志/结果元数据读取请求耗时与尝试次数。
6. 自动化测试覆盖单次请求、超时重试和非暂时性错误不重试；本地 Nest build、Jest 和浏览器真实模型生成仍需单独验收。

## 3.20 通用空间表面协议与人物地面运动（P0/P1）

### 目标

统一区分实体阻挡、可支撑表面和可行走表面。碰撞不是“障碍物”的同义词：实体可以阻挡穿越，同时其顶部仍可支撑人物；坡面/楼梯表面可以同时支撑并允许人物沿面移动。

### 模型定义协议（P0）

在 `modelCapabilityManifest.capabilities.spatial` 下增加可选 `surfaces[]`，保持声明式、开放扩展：

```js
surfaces: [{
  id: "stable-surface-id",
  targetPartId: "stable-component-id",
  shape: "mesh",
  supportsStanding: true,
  walkable: true,
  enabled: true
}]
```

- `targetPartId` 必须引用模型内真实的稳定 `userData.componentId`。
- `shape: "mesh"` 表示以目标部件内真实 THREE.Mesh 几何为依据；不以 Mesh 名称或人为生成的粗略 AABB 代替表面。
- `supportsStanding` 与 `walkable` 独立：可以站立的平台不一定允许沿其表面通行。
- 表面法线、世界变换和实际高度由 Runtime 从几何计算，不由 AI 编造。
- `colliders[]` 继续表达实体阻挡；同一几何可以同时具有实体阻挡与顶部支撑属性。
- 未知字段保留；缺少声明不自动推断为可站立/可行走。

### P0 实施边界

- AI 新建和微调 Prompt 都要求按实际几何声明 surfaces。
- Runtime 通过稳定 componentId 解析目标 Group，并收集其真实后代 Mesh。
- 沙盒 CollisionWorld 以模型实例 ownerId 注册/移除 support surface 句柄；模型替换、删除和空间刷新时同步维护。
- 注册仅表示数据接入，不代表人物控制器已经消费表面，也不代表楼梯/坡面已可走。

### P1 人物地面运动

- 人物控制器需从注册表查询脚下/前方实际三角面，计算世界空间高度和法线。
- 人物碰撞体与地面支撑分离；地面接触不能被当作穿模或普通障碍。
- 基础验收：地面站立、平台上落地、从平台边缘跌落、坡面移动受最大坡度限制、模型 Transform 改变后表面跟随。
- 楼梯连续踏步、跨台阶、跳跃、复杂凹凸网格和室内楼层导航需单独验收；P0/P1 不提前承诺完整支持。
- 任何未接入 Player Runtime 的表面声明均为数据声明，不得显示为“已可行走”。

### 约束

- 不按建筑、楼梯、桌子、车辆等模型类别编写专用物理规则。
- 不用整模型 AABB 替代真实表面；不把所有 Mesh 自动视为可行走。
- 不改变现有 XZ 阻挡协议和门状态优先级；用户 capability override 仍高于模型状态条件。


### P1 实施拆分补充（2026-11-08）

P1 分为两个可独立验收的子阶段，避免将射线检测等同于完整角色物理：

- **P1a — 近邻支撑面高度求解**：人物移动后从角色脚下附近向下 Raycast，仅查询已声明且已注册的真实 Mesh；依据世界空间法线过滤超过最大坡度的表面，并更新角色眼高。默认世界地面仍保持 Y=0 / 角色眼高 1.7。
- **P1b — 重力与离台跌落**：引入垂直速度、重力积分、落地状态和平台边缘离台检测；没有命中支撑面时不得瞬间传送回默认地面。P1b 未完成前，不得宣称已经支持平台边缘跌落。
- 当前不实现跳跃、连续楼梯踏步和复杂动态刚体。


### P1b 重力、落地与行走语义（2026-11-08）

- 人物使用垂直速度与重力积分；地面/支撑面只在下降阶段参与落地，不再因一次射线命中而瞬间传送到高处平台。
- 默认世界地面为 Y=0，角色眼高 1.7；离开模型平台后自然下落并可落回默认地面。
- `supportsStanding` 表示允许作为落地点；`walkable` 表示允许人物水平移动经过该表面。仅站立表面可以落地，但人物不能沿其表面移动。
- `walkable` 表面同时可作为落地点；超过最大坡度的面不参与支撑/通行。
- 上台阶高度限制为 0.45 世界单位；更高的平台不能被地面检测直接吸附。动态平台、跳跃、连续楼梯踏步和复杂角色胶囊体仍不在本子阶段范围。
- 角色移动帧和静止帧都更新垂直运动；自动寻路与键盘移动共享同一垂直运动解算。


### P1c 台阶跨越与连续楼梯行走（2026-11-08）

- 键盘移动和自动寻路统一经过水平目标位置的支撑语义检查。
- 角色站在支撑面上时，目标位置若是 walkable 表面且高度增量不超过最大台阶高度（当前 0.45），允许跨越并落到新踏步。
- 目标位置若存在 supportsStanding=true 但 walkable=false 的表面，禁止水平进入。
- 目标位置没有任何模型支撑面时，允许离开平台边缘，随后由重力系统接管下落；不能将“无目标支撑面”一律视为墙。
- 超过最大台阶高度的上行移动被阻止；向下离开平台不受此上行高度限制。
- 连续楼梯依赖模型提供真实、连续或逐级可命中的 walkable Mesh 表面；不按楼梯类别硬编码，也不自动推断楼梯几何。


### P1c 回归审查补充（2026-11-08）

- 垂直运动在无水平输入时仍须驱动当前相机模式的跟随更新；否则角色从平台边缘跌落时，玩家坐标变化而镜头停留在旧高度。
- 回归覆盖应同时检查键盘移动、自动寻路、静止下落、默认地面落地、模型支撑面落地、台阶高度限制与站立/行走语义。
- 单元测试源码存在不等于测试通过；本阶段仍需本地 Vitest、构建和浏览器实测。


## P2.1 Transform 联动统一（本轮增量）

- 引擎新增 `setSandboxModelTransform(id, patch)`，统一接收 position / rotation / scale 的轴向增量。
- 程序化 Transform 修改后同步更新世界矩阵、碰撞体、支撑面和阴影贴图。
- TransformControls 使用 `objectChange` 作为实际对象变换事件；普通 `change` 仅请求重绘，避免相机/控件变化时重复重建空间注册。
- 页面自然语言移动/旋转命令改为调用引擎 Transform API，不再直接修改 Object3D。
- 后续新增任何模型变换入口必须调用该 API；直接修改 Object3D Transform 后必须显式调用统一同步入口。


## P2.2 模型实例生命周期一致性（本轮增量）

- 引擎统一通过 `removeSandboxModelSpatialRegistration(ownerId)` 清理实例拥有的碰撞体与支撑面；替换、删除和引擎销毁共用该入口。
- 新增模型时拒绝重复实例 ID，防止 Map 覆盖旧实例但旧 Object3D 仍留在场景中的注册分裂。
- 模型替换默认继承原实例的 `worldState` 与 `environmentOverrides`；显式传入的新实例数据优先。
- 模型复制时深克隆材质引用的纹理，避免删除副本释放共享纹理而影响原实例。
- 存档对象列表以引擎实例注册表为权威来源；恢复时先解析全部模型，再注册，并在注册失败时回滚已注册实例。
- 页面删除操作仅在引擎确认删除成功后更新辅助引用表。


## P2.3 模型入场链路一致性（本轮增量）

- Worker 执行生成源码时记录能力 Manifest 的来源：模型模块显式导出，或由旧版参数/环境绑定兼容生成。
- AI 编辑后，若新源码显式导出 Manifest，则以 Worker 实际执行的源码 Manifest 为准；服务端响应中的 Manifest 作为兼容回退，避免 API 包装层回退旧 Manifest 覆盖新模型定义。
- Manifest 来源标记只作为前端数据优先级元数据，不进入模型能力定义本身；不改变 Worker 隔离、Runtime 注册和用户 capability override 优先级。


### P2.3 增量补充：部件元数据来源一致性

- Worker 对模型模块显式导出的 `modelParts` 记录来源标记。
- 编辑替换时，显式导出的部件列表优先于服务端响应中的兼容数据；显式空数组表示清空部件，不得被旧 API/当前模型部件覆盖。
- 仅对未导出部件列表的旧模块，才回退服务端响应或当前模型元数据。


### P2.3 空间 Runtime 注册回归验证

- 将模型实例空间注册刷新逻辑收敛为 `refreshModelSpatialRegistration`，统一按当前 Object3D 与当前 Manifest 重建碰撞体和支撑面。
- 刷新前按 ownerId 清理旧碰撞体和旧 Mesh 支撑面句柄；新声明缺失/清空时不保留旧注册。
- 通过 CollisionWorld 实例级测试覆盖：旧墙/旧地面替换为新墙/新地面、移除全部空间声明、Transform 后世界矩阵更新。
- 这些单元测试仅证明注册表数据变化，不替代 InputController 的真实人物通行/站立浏览器验收。


### P2.3 Capability Override 与存档恢复回归

- AI 编辑替换模型时，Worker 以旧 Capability Control Document 为 previousDocument，重新生成 AI inference proposals，但保留用户 overrides、diagnostics 和扩展字段。
- 回归测试必须验证：替换 Manifest 更新后，用户对具体部件碰撞能力的 override 仍然优先于新模型声明。
- 存档沿用 Object3D JSON，模型 userData 中的 Manifest 与 Capability Control Document 应一同持久化；恢复后必须重新从恢复对象注册碰撞体和支撑 Mesh，不能复用旧场景 Mesh 引用。
- 验收需区分声明持久化、Runtime 注册重建与人物实际物理行为；本阶段单测只覆盖前两项。


## P2.4 通用交互 Action Runtime（本轮增量）
- 兼容性：交互配置显式提供 `targetId` 时，状态动作可更新同一沙盒内的另一个模型实例；未提供时默认更新交互所属实例。

- Interaction Detection 负责定位最近交互入口；Action Runtime 负责解释入口上的声明式动作。
- 首批受控动作：`toggle`（兼容旧 `toggle-state`）、`set`、`rotate`、`translate`。
- `toggle/set` 更新所属模型实例的 `worldState`；`rotate/translate` 修改稳定 `componentId` 指向的部件局部 Transform，默认目标为交互入口部件，也可指定同一模型内其他部件。
- Transform 动作完成后更新世界矩阵、碰撞体、支撑面和阴影；状态动作沿用 `setSandboxModelState`，保留门状态条件和空间注册刷新。
- 动作协议不接受任意属性路径、回调、脚本或动态执行代码；未知动作安全失败。
- `enter` 已在 P2.5 接入同模型内部空间单层入场/退出；`pickup/drop` 仍未实现。

### 验收标准

1. 旧 `toggle-state` 门/灯声明保持兼容。
2. `toggle` 与 `set` 更新实例状态，并由现有 stateBinding 更新视觉/碰撞表现。
3. `rotate` 与 `translate` 只修改目标部件局部 Transform，并刷新空间注册。
4. 未知动作、缺失目标部件、无效数值不产生场景副作用。
5. Object3D 存档恢复后，交互配置随部件 userData 保留。
6. 自动化测试源码覆盖动作协议；真实 AI 生成和玩家按 E 端到端仍需浏览器验收。


## P2.5 同模型内部空间入场与退出

### 设计边界

- 进入的是模型自身生成的内部几何，不创建按建筑类别区分的独立室内模板。
- Manifest 使用 `capabilities.interior.entryPoints[]` 声明稳定入口 ID、目标部件 ID 和部件局部地面坐标。
- 外部交互部件声明 `{ action: "enter", entryPointId }`；内部出口交互部件声明 `{ action: "exit" }`。
- Runtime 解析目标部件世界变换，将玩家移动到内部地面点并增加角色眼高；通过 InputController 传送入口重置垂直速度、落地状态、导航路径和按键状态。退出时恢复进入前玩家坐标、相机模式及视角参数。
- 内部楼板必须声明真实 Mesh walkable surface；墙体/门洞继续使用空间 collider 表达。入口传送不替代室内物理和碰撞声明。
- 本阶段只支持单层内部空间的进入/退出；楼层切换、楼梯、电梯、房间导航、门锁条件和连续开门动画不在范围内。
- 不创建独立室内副本，不隐藏/重建模型外壳；外部世界和模型内部几何仍在同一 Three.js 场景中。

### 验收标准

1. 只有 Manifest 声明且目标 componentId 存在的 entryPoint 才能进入；入口世界坐标若落在当前碰撞体内则拒绝传送，不将角色推到墙外。
2. entryPoint 局部坐标经模型/部件父级变换后，解析为正确世界坐标。
3. 玩家进入后保留当前第一/第三人称模式；退出恢复进入前坐标与模式。
4. 未声明入口、缺失目标部件、重复进入、非当前内部模型退出均安全失败。
5. AI 新建与编辑 Prompt 使用同一入口/出口声明协议。
6. 单元测试覆盖坐标变换与失败路径；玩家真实穿门、室内行走、退出的浏览器验收仍需执行。


### 3.14 AI 模型视觉质量检测与自动修正

模型生成成功不等于视觉质量合格。新建程序化模型必须在浏览器端由真实 Three.js 预览渲染后，再进入视觉质检：

- 浏览器预览从实际模型采集正面、侧面、顶部和等轴四个视角；截图来自 WebGL RenderTarget，避免把模型源码或参考图误当作生成结果。
- 视觉模型同时接收原始提示词、可选参考图、四视角渲染图及几何诊断证据，返回结构化评分、是否通过、可观察问题、严重程度、关联稳定部件 ID 和最小修复建议。
- 视觉检查与几何诊断互补：视觉模型负责外观、比例、结构完整性和多视角一致性；几何诊断只提供顶点、变换和边界证据，不能仅凭 AABB 重叠判定缺陷。
- 对 critical/major 且具有明确修复指令的问题，复用现有模型微调接口做定向修正；每次修正后重新执行 Worker、重新渲染和复检，最多自动修正两轮。
- 自动修正必须保留模型身份、稳定 componentId、参数、能力声明及交互结构；不允许为消除视觉告警而无依据地改动无关结构。
- 视觉质检服务不可用、截图缺失或响应无效时，状态必须标记为“质检未完成”，不能伪装成通过，也不应丢弃已经成功构建的模型。
- 两轮后仍未通过时保留模型、质检报告和问题列表，交由用户决定是否继续人工/对话调整。
- 视觉分数是模型辅助判断，不是物理正确性或功能正确性的证明；碰撞、通行、室内导航、交互仍需独立 Runtime 验收。


### 3.20 沙盒模型全景选址、占地预览与显式落地确认

模型实例重新选址采用 **Overview Placement（全景选址）**，不再通过点击地面逐级缩小镜头。用户需要在同一全局视野中判断模型与沙盒空间的相对位置。

1. **进入全景选址**：切换到 overview，相机完整展示沙盒世界边界；记录进入前相机模式和角色输入模式。选址期间暂停角色移动，但允许用户按需使用总览相机控制。
2. **模型预览**：模型以半透明 Ghost 显示，鼠标移动时预览模型位置；模型底部同步绘制最大水平占地范围，当前实现使用模型世界包围盒在 XZ 平面的投影矩形，并提供填充与边界线。
3. **候选位置锁定**：鼠标移动只更新预览，不代表候选位置已确认。单击地面仅锁定候选坐标，不提交 Transform、不注册新实例、不写入存档，也不改变全景相机视野。点击“重新选择”解除锁定并继续预览；再次点击地面可锁定新候选点。
4. **显式落地确认**：左侧选址专用面板显示模型名称、占地宽深、候选坐标和状态。只有点击“确认落地”才恢复实体材质、正式更新已有实例 Transform 或注册新实例，并由页面触发存档。
5. **取消与回滚**：取消已有模型移动恢复原位置/旋转/缩放/可见性；取消新模型移除临时预览并释放资源。确认或取消后恢复进入选址前的相机模式和角色输入模式。

输入所有权：
- 选址期间左键由放置处理器独占；左键点击地面只锁定候选位置，不执行确认。
- 预览阶段的鼠标移动更新模型 Ghost 与地面占地轮廓；候选锁定后预览冻结，直到显式点击“重新选择”。
- 页面“保存沙盒”在选址期间禁用，防止把尚未确认的临时 Transform 写入存档。
- 选址专用面板暂时隐藏 AI 建模、对象列表、环境和任务等非当前操作功能。

占地范围语义：当前绘制的是模型世界 AABB 的水平投影，适用于快速判断最大水平占用边界；它不是复杂凹凸几何的精确底部轮廓，也不代表碰撞/可放置性预检。斜坡、平台表面吸附、地形适配、碰撞重叠和障碍区域禁放仍需独立实现与验收。


## 3.21 沙盒模型选择与操作入口（2026-11-09）

对象选择与对象操作必须分离，避免单一鼠标手势隐式触发编辑器、TransformControls 或镜头控制状态切换。

- **单击模型**：只选中模型实例；显示轻量轮廓高亮，并将左侧面板切换为当前对象上下文。不得自动打开模型编辑器或挂载 Transform Gizmo。
- **单击空白地面**：清除当前对象选择和轮廓高亮，左侧面板返回基础工具上下文。
- **双击模型**：不绑定编辑、放置或其他业务动作；重要操作必须通过可见的显式按钮触发。
- **对象上下文面板**：选中对象后提供“重新选址”“精细调整”“编辑模型”“复制”“删除”。无可编辑程序化源码的对象禁用“编辑模型”，不得进入空编辑器。
- **精细调整**：仅点击“精细调整”后挂载 TransformControls；位置、旋转、缩放是该状态内的子模式；点击“完成调整”解除 Gizmo 并恢复镜头输入。
- **重新选址**：采用 3.20 定义的全景选址、Ghost 占地预览、候选位置锁定和显式落地确认；不再通过点击地面逐级缩小镜头。
- **编辑模型**：仅显式按钮打开独立 ProceduralModelEditor；不再由双击或普通选择触发。
- **输入所有权**：普通选择状态下 OrbitControls 保持可用；精细调整状态下 TransformControls 独占模型手势并暂停 OrbitControls；选址期间继续由放置输入处理器接管左键。

该交互规范不改变模型实例数据结构、AI 生成协议、碰撞/支撑面 Runtime 或沙盒存档格式。


## 3.22 MVP 空白世界与模型落地冲突检测（2026-11-09）

### 范围

- 本决策仅作用于 `/world-sandbox-mvp`，不删除或修改正式校园地图、校园编辑器、校园空间数据，也不删除原 RPG 样板场景模块本身。
- MVP 初始化不再加载 `createRpgSampleScene`；改用独立空白沙盒场景，只创建基础地面、远景地面和世界边界。旧样板中的教学楼、道路、树木、水渠、桥、廊架、路灯、花坛、角色装饰均不进入 MVP 默认场景。
- 保留既有沙盒世界尺寸、相机、人物控制、环境系统、模型生成/编辑、存档和模型交互能力。
- 场景中的内容由用户生成并正式加入的模型实例逐步构建，不预置任何校园建筑或景观。

### 落地冲突规则

- 模型 Ghost 预览时计算其世界包围盒，并检测与其他已登记沙盒模型的水平/垂直包围盒是否重叠。
- 同时检查 CollisionWorld 中已登记的碰撞区域，避免绕过模型级检测的既有空间阻挡。
- 发生冲突时，占地预览变为红色，左侧面板显示冲突对象/区域，确认落地按钮禁用。
- 用户锁定候选位置后，确认函数再次执行冲突检测；不能依赖 UI 禁用状态作为唯一保护。
- 移动已有模型时排除自身实例及自身 ownerId 碰撞注册，避免与自己冲突。

### 精度与边界

- 当前模型占地采用世界 AABB XZ 投影，并以 Y 轴包围范围辅助区分上下层空间；旋转或不规则模型可能产生保守误判。
- CollisionWorld 中多边形区域当前按 AABB broad-phase 检测，可能保守拒绝多边形凹角附近的有效位置；不宣称已完成精确 Mesh/多边形相交求解。
- 空白 MVP 场景没有预置地形障碍；未来加入地形/静态设施时，必须将其空间碰撞注册到同一检测链路，不能只添加视觉 Mesh。
- 当前不处理斜坡贴地、地形高程吸附、复杂网格精确布尔相交和动态刚体。

### 验收标准

1. MVP 首次初始化只显示空白地面与世界边界，不出现旧样板建筑、道路、树木、水体、桥梁、廊架和装饰。
2. 正式校园地图与编辑器不受影响，`createRpgSampleScene` 文件仍可供其他明确使用该样板的页面调用。
3. 空白场景中可生成模型、移动人物、设置环境、保存/恢复模型并触发模型交互。
4. 两个模型占地重叠时，预览红色、显示冲突对象且不能确认；不重叠时可正常确认。
5. 移动已有模型时不与自身碰撞；确认时重新检测，防止候选锁定后场景变化导致穿模。
6. 本次代码更新不等同于构建或浏览器验收通过；仍需本地构建、自动化测试和真实交互回归。

## 3.23 连续世界与按需区块扩建（2026-11-09）

### 产品决策

- MVP 使用一个连续、统一坐标系的世界；世界可以向北、南、东、西按需扩建。
- 不强制划分校园区、生活区、商业区等功能分区；模型、道路、设施可在任意合法位置自由建造。
- 区域分组仅是可选的后续组织能力。用户可自行框选、命名和分组；不分组不影响放置、移动、碰撞或人物通行。
- 扩建是增加空间，不是缩放世界。既有模型、角色和世界对象的世界坐标不得因扩建而平移或缩放。
- MVP 先实现有限区块的显式扩建，不引入无限世界流式加载、自动卸载或复杂分区调度。

### 当前实现范围

- 初始世界由一个 54 × 42 世界单位地面区块组成。
- 每次向一个方向扩建时，增加该方向完整边缘的一排区块；支持连续扩建多层。
- 世界边界和 sampleBounds 随区块集合更新；地面区块保持统一尺寸与无缝相邻。
- walkableBounds 作为共享边界对象原位更新，使人物移动与 CollisionWorld 使用扩建后的范围。
- 模型选址世界边界、overview reset 范围和相机最大轨道距离同步读取扩建后的世界尺寸。
- 选址面板提供四方向扩建入口；无选中对象时的世界空间面板也提供四方向扩建入口。
- 沙盒存档新增 world 区块状态，恢复时先恢复世界区块，再恢复模型实例；旧版本存档仍可读取并默认使用初始区块。

### 验收标准

1. 初始世界只生成一个基础区块；向任一方向扩建后新增完整相邻边缘，不产生缝隙或重叠。
2. 连续向同一或不同方向扩建，区块不重复创建，世界边界准确增长。
3. 扩建前后已有模型和玩家世界坐标不变。
4. 人物可以进入新增区块；世界边界、模型选址和相机视野使用相同的更新后范围。
5. 保存并刷新后，已扩建区块与模型一起恢复；旧版本存档仍能恢复。
6. 功能分组不是强制数据层级，不影响自由放置。
7. 当前代码修改未经过本地构建、自动化或浏览器验收，不得标记为端到端通过。

## 3.24 沙盒/模型管理模式与外围地块回收（2026-11-09）

### 管理模式

- 页面提供“沙盒管理”和“模型管理”两个一级入口。
- 沙盒管理负责世界尺寸、四方向扩建/回收、环境时间/天气/降雨/风力/人工灯光，以及场景信息。
- 模型管理负责模型列表、选择、位置/旋转/缩放、重新选址、复制/删除、AI 模型创建与编辑。
- 切换管理模式只切换管理面板，不调用引擎 Transform/相机重置接口；当前模型选择和精细调整状态保持不变。
- 保存入口继续保留在全局页头；世界区块回收和扩建都标记为未保存变更，用户显式保存后写入现有 v4 存档。

### 外围地块回收

- MVP 仅支持回收北、南、东、西最外侧完整一排/一列区块，不允许内部挖空。
- 回收前由引擎检查边缘区块是否包含玩家、沙盒模型包围盒或已登记碰撞区域；有占用时拒绝操作并返回阻塞对象说明。
- 保留初始 (0, 0) 区块作为稳定锚点；世界至少保留一个区块。不能回收包含锚点的边缘。
- 成功回收后释放地面几何/材质资源，更新 chunk 索引、世界边界、sampleBounds、worldChunks、人物移动边界、CollisionWorld 边界和相机最大轨道距离。
- 世界区块仍使用现有 v1 world.chunks 状态结构；无需升级 v4 沙盒存档版本，保存/恢复流程沿用现有机制。

### 本轮验证要求

1. 四方向分别回收、连续回收及多次扩建后回收，世界区块始终为连续矩形。
2. 回收不能删除 (0, 0) 锚点或把世界缩减到零区块。
3. 玩家或模型包围盒占用目标边缘时，回收应被拦截；清空占用后可以回收。
4. 回收后保存并刷新，区块集合、边界与模型世界坐标保持一致。
5. 沙盒/模型模式切换不重置当前模型选择、Transform Gizmo 或模型放置流程。
6. 当前远程新增测试尚待本地执行；未完成构建、自动化和浏览器验收前，不标记为通过。


## 3.25 任意单块区块回收（纠正 3.24 的外围回收理解）

- 世界区块集合允许稀疏分布；world.chunks 是实际存在区块的权威集合，bounds / sampleBounds 只表示外接矩形，不代表矩形内部全部可行走。
- 回收 API 使用 removeWorldChunk(x, z)，只移除指定单块；禁止移除初始锚点 (0, 0)，至少保留一个区块。
- 回收前由 Engine 检查玩家位置、模型世界 Box3、已登记障碍物和支撑面；任一占用目标区块即拒绝。
- CollisionWorld 使用实际区块矩形集合约束玩家移动；相邻区块接缝保持连续，缺失区块成为不可进入区域。
- 扩建只增加外接矩形边缘的新层，不得补回或覆盖内部缺失区块。
- 存档继续使用现有 world.chunks，允许非矩形集合；恢复时校验坐标唯一性、锚点和区块数量。
- UI 必须先选择单块，再执行回收；中心锚点明确标记为不可删除。
- 视觉边界、地面洞口边缘和人物脚底表现仍需浏览器验收；不得仅凭数据层测试宣称完整体验通过。


## 地块管理交互补充（2026-11-09）

- 地块管理使用独立全景空间画布，不使用坐标菜单/列表作为主要操作界面。
- 画布至少支持全景查看、缩放、平移、单块选择、多选和批量回收。
- 批量回收必须逐块执行既有占用/锚点安全校验；失败地块保留并展示原因，成功地块可独立提交。
- 此交互层不得改变世界区块数据协议、坐标系或现有模型/玩家占用检测。


## 地块管理交互决策修订（2026-11-09）

地块管理的主操作界面必须是现有 Three.js 沙盒场景本身，而不是独立 SVG/俯视菜单地图。管理模式下在真实地面区块上显示边界和选中覆盖层，场景模型保持可见；用户直接点击场景地面选择单块，Ctrl/Cmd/Shift 点击多选。批量回收仍逐块调用原有占用校验，管理态不能绕过玩家/模型/碰撞占用保护。退出管理时隐藏地块覆盖层并恢复角色移动。


### 视角控制决策修订（2026-11-09）

- 沙盒构建/地块管理使用独立自由总览镜头，不继承 2.5D 地图的固定朝向限制；允许旋转、平移和大范围缩放。
- 进入地块管理时，按当前全部有效地块的整体边界计算中心点与取景范围；不能固定在初始地块或人物出生点。
- 扩建、回收、恢复世界后，如果当前处于总览模式，重新按世界边界适配镜头；用户继续操作时仍可自由移动观察中心。
- 人物探索继续使用第三人称/第一人称跟随镜头。进入地块管理时暂存当前镜头模式并暂停人物移动；退出时恢复原探索模式和人物控制。
- 构建镜头与人物跟随镜头是两套职责，不允许人物位置持续拉动构建镜头，也不允许构建镜头状态覆盖人物探索状态。
